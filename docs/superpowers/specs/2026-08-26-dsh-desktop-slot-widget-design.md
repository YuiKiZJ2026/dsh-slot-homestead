# DSH 桌面老虎机交互原型设计规格

> 已被 `2026-08-26-dsh-desktop-native-plugin-design.md` 取代。本文只保留原始产品规则与视觉背景，不再作为生产架构或发布依据。

- 日期：2026-08-26
- 状态：已取代（浏览器原型历史规格）
- 交付类型：可运行的浏览器端交互原型
- 技术路线：React + TypeScript + Canvas

## 1. 背景与产品定位

DSH 桌面老虎机是一个常驻桌面右下角的像素风工作陪伴组件。它把真实工作成果转换为硬币，再通过老虎机产生金币或纯装饰收藏品。收藏品被摆放在老虎机周围的小桌子和展示架上，使桌面微缩世界随工作积累逐渐丰富。

产品核心不是赌博或功能抽奖，而是“真实工作 → 可见奖励 → 收藏成长”的轻量反馈循环。随机系统只影响装饰性结果，不得控制 DSH 的模型、工具、Token、审批权限或其他生产能力。

## 2. 目标

1. 交付一个可在本地浏览器直接运行的高完成度交互原型。
2. 在模拟桌面右下角展示一个正面朝向用户、具有 2.5D 深度的像素老虎机与厚木桌。
3. 完整演示任务、验证和专注时长如何产生硬币。
4. 完整演示投币、拉杆、转轮、组合判定、金币返奖、收藏品掉落和自动摆放。
5. 提供收藏柜与商店，使硬币既可继续游玩，也可购买指定收藏品。
6. 使用统一 DSH 事件适配器，使模拟数据未来可替换为真实 DSH 数据而无需重写游戏规则。
7. 本地持久化钱包、每日进度、保底计数、收藏品和展示位。

## 3. 非目标

- 不制作原生安装包；首版通过本地开发服务器运行。
- 不连接真实 DSH 服务、账户系统或云同步。
- 不提供付费硬币、现金价值、提现、交易或社交排行榜。
- 不把模型、工具、Token 优惠、审批或生产功能放入随机奖励。
- 不制作复杂房间背景、完整操作系统模拟或大规模收藏品编辑器。

## 4. 核心体验

### 4.1 主画面

原型以一张安静、低对比度的模拟桌面为全屏背景。老虎机微缩组件固定在右下角，默认占视口宽度约 25%～30%，并随视口按整数像素倍率缩放。组件轮廓之外不使用 UI 卡片底板。

木桌前缘接近水平并向屏幕后方延伸。老虎机正面朝向用户，正面转轮是第一视觉重点；只显示顶部和少量右侧厚度，以保留 2.5D 空间感。不得采用令正面明显偏离用户的大角度等距斜放。

演示控制台位于左侧并默认收起。它不属于正式小组件视觉，只用于触发模拟 DSH 事件和检查状态。

### 4.2 核心交互顺序

1. 用户点击桌面硬币或“投币”热区。
2. 系统确认余额至少为 1，并立即锁定本次抽取结果。
3. 一枚硬币飞入投币口，钱包扣除 1 枚。
4. 拉杆进入可操作状态；用户点击或向下拖动实体拉杆。
5. 三个转轮依次启动，并按左、中、右顺序停下。
6. 系统高亮最终组合。
7. 金币沿立体抛物线从出币口飞出，或收藏品从出币口出现。
8. 金币进入钱包和桌面钱堆；新收藏品自动移动到下一个空展示位。
9. 状态返回空闲，允许再次投币。

投币即创建一个已经付费且结果锁定的 spin，硬币从此不可取消退回；拉杆只启动该 spin 的表现流程。用户投币后尚未拉杆便刷新页面时，应用恢复到“已投币、可拉杆”状态。转轮已经开始后刷新页面时，应用直接恢复并完成同一锁定结果。

余额不足时，投币口轻微抖动，硬币计数闪烁一次，并提示可通过工作或等待次日赠币获得硬币。不得播放虚假中奖或付费引导。

### 4.3 收藏与商店

点击桌面上的收藏入口后，收藏柜从组件边缘展开；关闭后恢复纯微缩场景。收藏柜显示已拥有、未拥有、稀有度、套装进度和公开价格。

商店使用同一面板的独立标签页。已拥有的收藏品不能再次购买；老虎机抽到重复品时按规则自动折算为硬币。

### 4.4 Agent 状态反馈

DSH 状态会触发轻量、非阻塞的环境反应：

- 空闲：月亮灯缓慢明灭，植物轻微摆动。
- 工作中：老虎机面板出现低亮度流光，机器人显示工作指示灯。
- 任务完成：已展示收藏品依次弹跳一次，并出现少量像素闪光。
- 报错：机器人短暂缩回展示台，水晶亮度降低后恢复。

默认静音。用户开启声音后，投币、拉杆、转轮、金币和稀有收藏品可播放短促像素音效。

## 5. 视觉与渲染

### 5.1 美术方向

- 温暖、治愈、精致的独立游戏像素美术。
- 深海军蓝阴影、胡桃木棕、琥珀金币光和青绿色轮廓光。
- 清晰、硬朗、成块的像素簇；不使用模糊、抗锯齿或普通光滑 3D 渲染。
- 强调接触阴影、像素环境遮蔽、厚木材、金属机身和半透明水晶。
- 缩小后必须一眼识别老虎机、三个转轮、右侧摇杆、金币和收藏品。

### 5.2 Canvas 规则

老虎机组件 Canvas 使用 384×288 的固定逻辑分辨率，并只按整数倍缩放。1280×720 与 1440×900 下使用 1 倍 CSS 尺寸；更大屏幕只在完整场景不会超过目标区域时切换到 2 倍。1024×768 下仍使用 1 倍，因此 25%～30% 只是常见桌面尺寸的视觉目标，不是所有视口的硬性比例。所有图像使用最近邻采样，CSS 设置 `image-rendering: pixelated`，Canvas 禁用图像平滑。

场景拆分为以下透明像素资源：

- 厚木桌与展示架底图。
- 正面朝向用户的老虎机机身。
- 三个独立转轮窗口与五种符号。
- 拉杆的空闲、下拉和回弹状态。
- 硬币、闪光及出币粒子。
- 十二件独立收藏品。

新视觉资源必须重新制作；先前的大角度斜放图片只作为风格参考，不作为最终交互底图。

### 5.3 动画时序

| 阶段 | 默认时长 |
|---|---:|
| 投币 | 300 ms |
| 拉杆下压与回弹 | 320 ms |
| 三轮旋转与依次停止 | 1,800～2,400 ms |
| 组合高亮 | 350 ms |
| 金币返奖 | 700～1,000 ms |
| 收藏品落下并归位 | 900～1,200 ms |

开启“减少动态效果”后，取消大幅弹跳和抛物线运动，将完整流程压缩至约 700 ms，同时保持结果和状态顺序不变。

## 6. 工作奖励经济

### 6.1 奖励来源

| 来源 | 奖励 | 限制 |
|---|---:|---|
| 每日首次打开 | 3 枚 | 不计入工作奖励上限 |
| 完成真实任务 | 1 枚 | 计入每日工作奖励上限 |
| 带测试或验证的任务 | 30% 概率额外 1 枚 | 计入每日工作奖励上限 |
| 有效专注满 1 小时 | 2 枚 | 可在当日连续累计 |
| 专注时长奖励上限 | 每日 16 枚 | 对应最多 8 小时 |
| 每日工作奖励总上限 | 25 枚 | 任务、验证和专注时间共用 |

不足一小时的有效专注分钟数在当天继续累计，跨本地自然日清零。每日边界使用运行设备的本地日期。若设备时钟回拨，系统依据已处理日期和事件 ID 防止重复赠币。

专注时间由 DSH 适配器提供“已判定有效”的分钟数。不得使用程序开启时长、Token 消耗或工具调用数量代替有效专注时间。

### 6.2 上限计算顺序

1. 每日首次打开的 3 枚直接进入钱包，不占用 25 枚工作上限。
2. 任务、验证和专注奖励均先计算理论奖励。
3. 实际奖励为理论奖励与当日剩余工作额度中的较小值。
4. 达到 25 枚后，后续工作事件仍被记录，但当日不再生成硬币。
5. 专注奖励还受 16 枚子上限约束。

## 7. 老虎机规则

### 7.1 成本与组合

每次成功投币消耗 1 枚硬币并创建一个结果锁定的 spin；拉杆本身不再次扣币。五种转轮符号为金币、叶子、水晶、月亮和机器人。

| 组合 | 奖励 |
|---|---|
| 三枚金币 | 5 枚硬币 |
| 任意位置两枚金币 | 返还 1 枚硬币 |
| 三片叶子 | 随机普通收藏品 |
| 三颗水晶 | 随机稀有收藏品 |
| 三个月亮 | 随机套装收藏品 |
| 三个机器人 | 优先获得一个未拥有的稀有收藏品，并获得 3 枚硬币 |
| 其他组合 | 无奖励 |

### 7.2 原型概率

结果由奖励引擎先抽取，再选择与该结果对应的转轮组合进行动画。随机数源可注入并在测试中固定；生产原型在扣币时把抽取结果持久化。这样可以保证刷新、掉帧或动画中断不会改变奖励。

| 结果类别 | 基础概率 |
|---|---:|
| 无奖励 | 45% |
| 两枚金币，返还 1 枚 | 24% |
| 三枚金币，获得 5 枚 | 8% |
| 普通收藏品 | 12% |
| 稀有收藏品 | 7% |
| 套装收藏品 | 3% |
| 机器人大奖 | 1% |

概率在收藏柜的规则页公开显示。原型不使用虚假擦边、动态改变概率或付费强化。

### 7.3 收藏品保底

连续 10 次没有获得新收藏品后，第 11 次在基础概率抽取之前强制执行保底。保底结果在尚未拥有的普通品和稀有品中按 75% / 25% 抽取；若其中一个池为空，则从另一个池抽取。全部普通和稀有收藏品已拥有时，保底改为 9 枚硬币并把保底计数归零，避免之后每次都触发硬币保底。

只有新收藏品实际进入库存时，连续未获得收藏品计数才归零。金币奖励、无奖励以及常规抽取到重复品并折算硬币，均使该计数加一。机器人大奖获得新稀有品时归零；稀有池已集齐而改为硬币时计数加一。

### 7.4 重复品与价格

| 稀有度 | 商店价格 | 重复品折算 |
|---|---:|---:|
| 普通 | 6 枚 | 3 枚 |
| 稀有 | 18 枚 | 9 枚 |
| 套装 | 30 枚 | 15 枚 |

商店只允许购买未拥有的收藏品。普通、稀有和套装的常规老虎机结果会从该稀有度的完整池中抽取，因此可能重复；重复品不会占据新的展示位。机器人大奖优先从未拥有的稀有品中抽取；若稀有品已经全部拥有，则发放稀有重复品折算的 9 枚硬币，再加大奖自带的 3 枚硬币。

## 8. 首版收藏品目录

首版固定提供十二件收藏品：

- 普通：小盆栽、书本底座、桌面时钟、热饮杯、迷你工具箱、纸灯笼。
- 稀有：发光水晶、月亮灯、迷你机器人。
- 套装：“星夜观测”三件套——星星投影仪、星座球、彗星徽章。

普通品以静态展示和轻微呼吸动画为主。稀有品具有独立待机动画、粒子或可选音效。集齐“星夜观测”三件套后，模拟桌面背景出现微弱星空纹理，老虎机金属边缘切换为星夜配色；不改变任何功能或概率。

展示位按前景、中景和后景分层。新收藏品自动放入第一个空位；用户可在收藏柜中选择“展示/收起”，但首版不提供自由拖拽布置。

### 9.4 DSH 内部事件协议

适配器输出以下事件类型：

```ts
type DshEvent =
  | {
      id: string;
      type: "task.completed";
      occurredAt: string;
      taskId: string;
    }
  | {
      id: string;
      type: "task.verified";
      occurredAt: string;
      taskId: string;
    }
  | { id: string; type: "focus.minutes"; occurredAt: string; minutes: number }
  | {
      id: string;
      type: "agent.status";
      occurredAt: string;
      status: "idle" | "working" | "completed" | "error";
    };
```

所有事件 ID 必须在数据源内全局唯一。奖励类事件依据 `id` 幂等处理；已处理 ID、已完成任务 ID、已验证任务 ID 和待处理验证事件均保留 30 天，超过 30 天的迟到奖励事件不再结算并写入演示日志。验证事件还依据 `taskId` 保证同一任务最多计算一次额外奖励，并且只有对应任务已完成时才结算；验证事件先到时进入待处理队列，等待完成事件。30% 验证奖励通过事件 ID 和固定版本盐生成可复现判定，并与事件处理状态在同一存档快照中写入，刷新不会重新抽取。Agent 状态事件只改变表现，不生成硬币。真实 DSH 接入时只需实现相同适配器接口。

## 10. 状态与持久化

存档至少包含：

- Schema 版本。
- 钱包硬币数。
- 单调前进的最后赠币日期，以及最近 7 天按日期分隔的工作奖励账本；每个日期项包含工作奖励总数、有效专注分钟、已结算专注小时数和专注奖励数。
- 最近 30 天的已处理事件 ID、已完成任务 ID、已验证任务 ID 和待处理验证事件。
- 连续未获得收藏品次数。
- 已拥有收藏品、展示位和套装状态。
- 静音、减少动态效果和组件缩放设置。
- 已锁定但尚未完成表现的完整老虎机结果，包括唯一 spin ID、最终三个转轮符号、具体金币数、具体收藏品 ID、是否重复、重复折算额、保底计数变化和结算阶段。

每次经济状态变化先生成完整新状态，校验通过后以单条序列化快照同步写入，并递增修订号。老虎机在扣币时即解析并写入完整奖励，而不是只保存奖励类别或随机种子；动画完成后再标记为已结算。投币后购买收藏品、切换展示位或刷新页面都不能改变已经解析的奖品。若页面在动画中刷新，重新打开时恢复同一已付费 spin：尚未拉杆则继续等待拉杆，已经启动则直接完成锁定结果，绝不重新抽取或重复扣币。

首版只允许一个活动写入标签页。应用使用 Web Locks API 持有名为 `dsh-slot-economy` 的独占锁；未取得锁的其他标签页进入只读镜像模式，只接收 `storage` 更新且不能投币、购买或处理工作奖励。取得锁的标签页仍在每次经济操作前后校验存档修订号。原型支持范围明确为现代 Chromium 浏览器；不支持 Web Locks 的环境显示兼容性提示并禁用经济写入。

若存档 JSON 无法解析或不符合 Schema，原始内容以带时间戳的诊断键保留，应用恢复为安全默认状态，并在演示控制台显示非阻塞提示。

每日首次打开依据运行设备的本地日期和 `lastAwardDate` 判断。只有当前日期严格晚于 `lastAwardDate` 才发放新一天的 3 枚；时钟回拨到相同或更早日期不再次发放。工作事件按 `occurredAt` 转换后的本地日期进入最近 7 天账本，超过 7 天的迟到工作事件只记录不奖励。纯本地原型无法抵御用户主动篡改系统时间，此限制在 README 中明确说明。

专注分钟按事件所属日期累计。每形成完整 60 分钟即产生理论 2 枚奖励并消耗该 60 分钟；若当日工作总额度只剩 1 枚，则实际发放 1 枚且该小时仍视为已结算，不结转未发放的另一枚。达到 480 分钟或实际获得 16 枚专注奖励后，当日后续分钟只记录为统计值，不再生成可奖励余数。

## 11. 演示控制台

控制台默认收起，提供以下操作：

- 模拟完成一个任务。
- 模拟任务验证通过。
- 增加 60 分钟有效专注时间。
- 切换 Agent 状态。
- 通过可控时钟模拟进入下一本地自然日。
- 检查钱包、每日额度、专注累计、保底计数和最后事件。
- 在仅限开发/演示模式下预设下一次老虎机结果，以稳定演示和端到端测试。
- 重置原型存档；执行前必须二次确认。

## 12. 可访问性与适配

- 投币和拉杆支持鼠标、触控与键盘。
- Canvas 只负责视觉绘制；透明 React DOM 热区承载投币、拉杆和面板交互，并提供焦点、键盘语义与 ARIA 名称。
- 焦点样式不得只依赖颜色。
- 所有图标按钮提供可访问名称。
- 默认静音，并提供独立音效开关。
- 遵循系统 `prefers-reduced-motion`，同时允许手动覆盖。
- 支持 1440×900、1280×720 和 1024×768；小尺寸下降低组件倍率，不裁切老虎机或桌子。

## 13. 错误处理

- 余额不足：不扣币、不启动抽取，只播放短促反馈。
- 重复事件：忽略奖励计算，并在演示日志中标记为重复。
- 负数或非有限数值：拒绝写入并恢复上一个有效状态。
- 资源加载失败：显示简化的像素占位轮廓，游戏逻辑保持可操作。
- 动画异常：跳到已锁定结果的最终状态并完成一次结算。
- 收藏池为空：按该稀有度的重复品折算额发放硬币。
- 本地存储配额或写入失败：保留内存中的上一有效状态，暂停新的经济操作，并提示用户导出或重置存档。

## 14. 测试策略

### 14.1 单元测试

- 每日首次赠币只执行一次且不占用 25 枚上限。
- 任务、验证和专注奖励共同受 25 枚上限约束。
- 每满 60 分钟发放 2 枚，不足部分当天累计。
- 专注奖励每日最多 16 枚。
- 跨日重置专注余数、每日额度和首次打开状态。
- 时钟回拨和重复事件不会重复奖励。
- 验证事件先于完成事件、同一任务多次验证和刷新重放时不会重复奖励。
- 概率结果映射到正确转轮组合。
- 固定随机种子或预设结果时，概率、保底和动画恢复测试完全可复现。
- 第 11 次保底、池为空和全收集行为正确。
- 商店余额、购买、重复品折算和套装完成正确。
- 刷新恢复已锁定结果时不重复扣币或返奖。
- 投币后未拉杆刷新时恢复为已付费、可拉杆状态。

### 14.2 组件测试

- 演示按钮生成正确 DSH 事件。
- 余额不足时拉杆不可启动。
- 收藏柜、商店、展示/收起和设置可操作。
- 静音和减少动态效果设置持久化。

### 14.3 端到端测试

自动执行并验证以下完整链路：

1. 首次打开获得 3 枚硬币。
2. 模拟任务和专注事件获得工作奖励。
3. 投币并拉动摇杆。
4. 三轮停止并结算金币或收藏品。
5. 收藏品进入库存并出现在桌面展示位。
6. 使用硬币购买未拥有的收藏品。
7. 刷新页面后状态保持一致。

### 14.4 视觉检查

- 在三种目标视口检查右下角定位与无遮挡。
- 检查老虎机正面朝向用户，顶部与少量右侧面仍可见。
- 检查整数缩放、最近邻采样和无抗锯齿。
- 检查转轮、拉杆、金币轨迹和收藏品在缩小状态下可识别。
- 检查控制台收起后没有外围 UI 卡片破坏微缩场景。

## 15. 验收标准

原型满足以下条件即可验收：

1. `npm install` 与 `npm run dev` 可启动应用。
2. 自动化测试全部通过。
3. 主场景在目标视口下稳定固定于桌面右下角。
4. 用户可完成至少一次完整投币、拉杆和返奖流程。
5. 模拟任务、验证和专注事件严格遵守已批准的经济规则。
6. 商店购买、收藏品自动展示、重复品折算和套装外观变化可演示。
7. 刷新不会丢失或重复结算经济状态。
8. 所有最终像素资源为正面朝向用户、透明背景、硬边无抗锯齿。

## 16. 后续真实 DSH 接入

原型完成后，真实接入只替换 `MockDshAdapter`。真实适配器负责把 DSH 的任务完成、验证、有效专注分钟和 Agent 状态转换为本规格定义的内部事件；经济、老虎机、收藏、渲染和存档模块保持不变。

如果 DSH 的真实事件协议与本规格不同，应在适配器边界转换，不把外部字段泄漏到游戏引擎。
